# Прокрутка готовой раскладки

Изменение `scrollLeft`/`scrollTop` у semantic HTMLElement переиспользует
готовый кадр Renderer, если содержимое и условия раскладки не менялись.
Этот путь общий для `overflow: auto`, `scroll` и программной прокрутки
`hidden`: компонент Markdown, Node или отдельный Display не участвуют
в выборе оптимизации.

При обычной раскладке Renderer сохраняет диапазоны записей потомков каждого
scroll-контейнера. Следующая прокрутка меняет их смещение, внутренние clips,
hit fragments и положение thumb. Сам контейнер, его рамка, внешний clip и
соседние поддеревья сохраняются. Вложенные контейнеры обрабатываются от детей
к родителям, в том числе когда обе оси нескольких контейнеров изменились
в одной Document transaction.
Для векторных путей также обновляются начало hit-геометрии и преобразования
их владельцев: масштабированная линия остаётся интерактивной там, где нарисована.

Переносы строк и размеры повторно не измеряются. Старый immutable кадр остаётся
неизменным. Новый кадр передаёт разреженный список изменённых paint-записей
через тот же canonical frame-change transport, который используется для
transform updates. WebGPU сохраняет текстовые объекты, геометрию и материалы.
Когда меняется только положение текста, он переиспользует подготовленные
начертание, цвет и неизменившиеся clips вместо повторной подготовки paint.

Изменение текста, CSS, состояния, влияющего на стили, шрифтов, размеров изображения
или viewport требует обычной раскладки. Открытые popover/select overlays тоже
оставляют обычный путь: их положение может зависеть от прокручиваемого anchor.
После такой раскладки scroll снова может переиспользовать новый кадр.

При прокрутке под неподвижным указателем меняется hover-цель. Renderer проверяет
уже разобранные CSS-селекторы: состояние инвалидирует раскладку только при
потенциальном совпадении `:hover`/`:active` с изменённым элементом и его
контекстом предков. Hover-стили другой панели в том же Document не мешают
прокрутке. Pointer enter/leave и действительно применимые стили сохраняются.

Сложность обновления зависит от числа перемещаемых paint/hit-записей.
Общая GPU-трансформация группы здесь не добавляется. Текст и изображения,
полностью отсечённые viewport/clips, исключаются из GPU render list. Для текста WebGPU кеширует
границы фактической stencil/cover-геометрии глифов, включая выступающий курсив,
а семантические узлы и геометрия остаются для возвращения в видимую область.

Проверки в `renderer/tests/scroll-frame.test.ts` сравнивают быстрый кадр с полной
раскладкой: обе оси, вложенность, масштабирование, скруглённые clips, inline
текст, textarea, изображения, пути, clamping, изменение документа и popover.
`webgpu/tests/scroll-frame.test.ts` проверяет сохранение объектов и геометрии
текста при последовательной прокрутке.

## Контрольный замер

2026-09-05, текущий MetaFor README, область 600×800, реальные Inter/JetBrains
Mono, 5 прогревочных и 30 измеряемых шагов по 80 px. В одном процессе сравнивались
принудительная полная раскладка и обычная прокрутка с переиспользованием.
Декодирование GIF и отправка кадра на GPU в замер не входят.

| CPU-этап | Полная раскладка, медиана | Прокрутка, медиана |
|---|---:|---:|
| Renderer | 113,31 ms | 3,28 ms |
| WebGPU backend | 6,67 ms | 5,40 ms |
| Весь шаг с обработкой колеса | 120,49 ms | 8,87 ms |
| Вызовы измерения текста | 19037 | 0 |

P95 всего CPU-шага: 139,82 → 10,69 ms. Это локальная проверка данного README,
не гарантия времени кадра для любого документа или GPU.

Этот первый замер не включал смену hover после scroll. Дополнительный прогон
того же README включал указатель над содержимым, hover-события и последующий
flush. Каждый шаг выполнялся в отдельной задаче event loop. Для сравнения
воспроизводилась прежняя безусловная hover-инвалидация: медиана CPU-цикла
112,82 → 9,26 ms, P95 135,04 → 15,35 ms. Измерение текста после hover: 19037 → 0.
Живой GPU-тайминг и FPS этим CPU-прогоном не измеряются.

Регрессии: `renderer/tests/hover-scroll.test.ts`,
`browser/tests/projection-input.test.ts`, `webgpu/tests/text-visibility.test.ts`.
