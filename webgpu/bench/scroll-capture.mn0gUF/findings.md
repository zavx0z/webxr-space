# Прокрутка редактора и нод: диагностика 2026-09-06

Это диагностический результат, не приёмка оптимизации и не замер чистого FPS.
Производственный код в ходе этого исследования не изменялся.

## Условия

- Checkout: `webxr-space/main`, HEAD `158f27a`, с существующим незакоммиченным
  срезом оптимизации Renderer/WebGPU/CodeEditor/Template.
- Страница: `@zavx0z/nodes/layout/fixed/baseline/down`.
- Загруженная ревизия Storybook: `2d5a188c4af78d087bad545b`.
- Chrome: 152.0.7977.75, Intel Mac; viewport 1920×1088 CSS px, DPR 2,
  Canvas 3840×2176. Видимость страницы подтверждена как `visible`.
- CPU throttling: 1×, network throttling отсутствует.
- Проверенный получатель колеса: HTML CodeEditor в правом Inspector.
  Одиночное событие сдвинуло строки 403 → 399, без движения нод.
- Нагрузочный ввод: `WheelEvent` через существующий native Canvas listener,
  deltaY попеременно −16/+16, deltaMode 0. Между событиями 32 мс; после
  события ожидался RAF. Это измеряет обработку события и следующий JS-кадр,
  но не аппаратный input-to-photon и не время исполнения всех GPU-pass.
- При отключении записи использовалась сбалансированная пара публичных
  `webgpuInspector.disableRecording()` / `enableRecording()` в `finally`.
  Сам Inspector оставался установленным: это не полностью чистый браузер.

## Контрольные прогоны редактора

Каждая серия: 4 прогрева + 20 измерений. Каждые 24 wheel-события дали
24 представленных кадра по счётчику приложения.

| Запись Inspector | Input median | До следующего RAF median | P95 |
| --- | ---: | ---: | ---: |
| включена | 0,40 мс | 515,0 мс | 1017,8 мс |
| отключена | 0,40 мс | 540,5 мс | 692,4 мс |
| снова включена | 0,40 мс | 567,3 мс | 655,2 мс |

Отключение записи не устранило задержку. Старые avgFrameMs/fps/bound из
Inspector не используются: demand-паузы попали в его расчёт refresh period.

## Ноды с исходниками и без

Та же страница, запись Inspector отключена, wheel в области NodeEditor.
Противоположные дельты возвращают положение после каждой пары событий.

- С исходниками, шесть event → RAF: 1316,0; 375,4; 371,2; 352,3; 350,1;
  343,3 мс. Input обычно 84–95 мс.
- С открытыми параметрами вместо исходников, восемь event → RAF: 174,3;
  182,6; 179,6; 161,0; 169,9; 184,2; 604,1; 155,7 мс.
  Input обычно 9–12 мс, один выброс 218,8 мс.
- После сравнения панель «Исходники» возвращена.

Открытые исходники существенно усиливают тормоза, но не являются единственным
источником. Это короткие контрольные серии, не статистически строгий A/B релизов.

## GPU capture ручной прокрутки

Сохранённый файл:

`webgpu/bench/scroll-capture.mn0gUF/before-manual.wgpuc`

Исходный `cap-3.wgpuc` скопирован сюда до повторного использования MCP-счётчика
capture IDs. После перезапуска MCP этот же baseline был загружен как `cap-1`. Номера команд и
объектов ниже относятся к содержимому файла, а не к новому прогону.

- 31 submit, 62 render-pass, 70 529 drawIndexed, 10 040 createBuffer.
- 51 439 924 байта writeBuffer; ошибок validation нет.
- 9260 из 10040 созданий соответствуют четырём буферам 2315 плоскостей:
  position 48 B, normal 48 B, UV 32 B, index 12 B. Остальные включают
  геометрию текста. Сам счётчик не доказывает утечку: нужно отличить первую
  загрузку вновь видимых объектов от повторного создания старых.
- Команда 11720 → Buffer 13078: `createAndUploadAttribute` →
  `getOrCreateGeometryBuffers` → `renderMesh`; команда 11731 рисует quad
  из шести индексов.
- В каждом первом проходе пары повторяется 1274 draw calls. Их идентичное
  количество не доказывает идентичность содержимого или возможность безопасно
  пропустить проход.
- GPU duration 8,258 мс присутствует только у pass 0. Остальные 61 pass не
  имеют таймингов. Нельзя трактовать это как полное время кадра, делать вывод
  `vsync-bound` или утверждать «100% времени GPU у первого прохода».
- Сообщение Inspector о повторных bind groups требует проверки dynamic offsets:
  одинаковый GPU объект группы с разными offsets не является лишним bind.

## История demand-loop

- В `834a5b2` от 2026-09-05 07:40 уже были `requestRender`, объединение
  запросов через `requestedFrame` и единичный `requestAnimationFrame`.
- `3198d2f` от 2026-09-05 21:34 добавил публичный frameloop/useFrame,
  before-render синхронизацию и подавление рекурсивного request во время
  подготовки (`preparing`).
- `158f27a` от 2026-09-06 01:15 перевёл владельцев проекций на Elements.
- В текущем воспроизведении задержка — длительная работа JS-кадра, а не
  полусекундный таймер планировщика. Виновный коммит не изолирован;
  одинаковые сценарии на прежних версиях браузерного приложения не запускались.

## Следующий проверяемый срез

1. В WebGPU проверить переиспользование одинаковых цепочек clipping и их
   coordinate spaces; сейчас подготовка и обновление повторяются для многих
   scalar rectangles. Сохранить подвижные/nested clips, границы и fail-closed.
2. Проверить повторные обновления матриц HUD/Space и CPU-работу неизменных
   проекций. Не подменять demand непрерывным рендерингом без доказательств.
3. Посчитать GPU-буферы при возврате на уже прогретые строки и подтвердить
   освобождение ресурсов отдельно от первого появления нового содержимого.
4. Повторить те же контрольные сценарии; получить тайминги всех GPU-pass.

DOM, Browser, Engine, Template, support inventories и production WebGPU-код
во время этой диагностики не изменялись. Storybook не останавливался.
